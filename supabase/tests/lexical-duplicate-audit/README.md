# 連點重複紀錄稽核

> 🟢 **全部唯讀。** 沒有 INSERT / UPDATE / DELETE / DDL，staging 與 production 都可以安全執行。
> 一次貼一份（Supabase SQL Editor 只顯示最後一個查詢的結果）。
>
> 這份稽核**只回答「有多少、長什麼樣」**，不修任何東西。要不要清、怎麼清是下一個決定。

## 在找什麼

PR #154 之前，四個作答模式用 `if (showResult) return` 當防線，而 `showResult` 是 React state ——
`setShowResult(true)` 之後、re-render 之前它仍然是 `false`，同一個 tick 裡的第二次點擊會穿過去。
留在資料裡的痕跡是：**同一位學生、同一個字、同一種題型、同一場 session，幾十毫秒內兩筆以上。**

| 檔案 | 要看什麼 |
|---|---|
| `00-preflight.sql` | 5 項檢查。第 3 項（毫秒精度）是 false 就不用往下跑了 |
| `05-by-exercise-type.sql` | 🛑 **先看這支。** 各題型的量與重複率 —— 確認稽核涵蓋到全部的列 |
| `01-overview.sql` | **主結果。** 組數、判定矛盾、多出來的列、熟練度多算幾次 |
| `02-by-day.sql` | 逐日趨勢。修正上線後應該掉到 0 —— 但要先確認那幾天真的有資料 |
| `03-contradictory.sql` | 判定矛盾的明細，含「可否自動判定」 |
| `04-mastery-impact.sql` | 依 學生×單字 列出熟練度被多算的程度 |
| `06-repair-preview.sql` | 🟢 唯讀。修正的 before / after 預覽。**07 之前一定要先跑這支** |

## 🛑 第一版錯了兩件事（留著當教訓）

第一版只看四種題型（`quick_quiz` / `fill_blank` / `synonym_antonym` / `spelling`），
因為修正是針對那四頁做的。實際跑下去，那四種只佔全表的 **2%** ——
量最大的 `srs` 完全在稽核之外，主結果那個 0 什麼都沒證明。

第一版還把 `match` / `flashcard` 當成「只留證據、不影響熟練度」的對照組。
那也是錯的：配對成功與 flashcard 的 Mark as Known 都走 `recordPracticeAttempt`，
一樣會動熟練度。

兩個錯同一個根源：**拿「我以為某個題型怎麼寫」當分類依據，而不是看資料自己記了什麼。**
現在改成涵蓋所有題型，並用每一列自己的 `affected_mastery` 來分類。

## 判定條件，以及為什麼是這樣

四個條件同時成立才算一組：**同學生 + 同單字 + 同題型 + 同 session + 相鄰兩筆 ≤ 2 秒**。

- 🛑 **不用 `correct` 分組。** 「快速點兩個不同選項」留下的就是一對一錯，
  那是最該抓的一類。用 `correct` 分組會整個漏掉。
- 🛑 **判定用 `judgment = coalesce(correct, self_rating)`，不是只看 `correct`。**
  SRS 的 `correct` 永遠是 NULL，真正的證據在 `self_rating`；
  只看 `correct` 的話，SRS 的「forgot + easy 連點」會被當成無衝突放行。
- **2 秒是刻意放寬的**（實際連點相隔幾十毫秒）。學生不可能在 2 秒內對同一場、
  同一個字、同一種題型真的作答兩次。
- **涵蓋所有題型**，用每一列自己的 `affected_mastery` 分類，而不是靠題型清單。
  `affected_mastery = false` 的列（配對誤點、翻卡曝光）本來就會密集重複，
  它們在 `05` 當量尺：會動熟練度的題型，重複率應該明顯低於它們。

## 判讀

**先看 `05`。** 主結果是 0 的時候，要先確認「合計列數」≈ 全表列數。
涵蓋不到的列，那個 0 不代表乾淨，只代表沒看。

再看 `02`：修正上線之後的日期應該是 0 —— **但那一欄只有在「當日總作答」不是 0 時才算數。**
上線後沒有資料的話，那個 0 什麼都沒驗證到。

`05` 的「只留證據」欄是量尺：那些列本來就會密集重複。
會動熟練度的題型重複率若與它們相當，代表時間窗量到的是
「正常的快速作答」而不是連點，**先別依它清任何資料**。

## 🛑 清不掉的那一類

`03` 的「可否自動判定」欄把判定矛盾分成兩種：

- **`timeout 可判定`** —— 其中一筆是倒數歸零自動記的（`metadata.event = 'timeout'`），
  另一筆才是學生按的。刪 timeout 那筆即可。
- **`⚠️ 無法判定`** —— 兩筆都是學生點的，只是點了兩個不同選項。
  **沒有任何欄位能還原學生本來要選哪一個。** 兩筆的時間差只說明哪一下先到，
  不代表哪一個是本意（很可能反而是後到的那個）。這一類不要猜。

## 🛑 刪 attempts 不會退回熟練度

熟練度在 `student_lexical_mastery`，是另一張表。
`record_lexical_attempt()` 當初就已經把 `review_count` / `correct_count` / `mastery_level` 推過去了。
刪掉 `lexical_attempts` 的列**不會**把它退回去 —— 所以 `04` 的數字才是
「真正影響到學生看到什麼」的部分，而重算熟練度是比刪列更大的一個決定。

## 🛑 舊表有稽核看不到的歷史

`user_word_progress`（學生實際感受到的那張）從 **2026-02-10** 就在收資料，
`lexical_attempts` 是 **2026-09-22** 才有的。舊表帶著七個月的歷史，這份稽核看不到。

後果很具體：

| | 可不可信 |
|---|---|
| 「多算幾次」 | ✅ 從 `lexical_attempts` 數出來的，是實際發生的重複 |
| 「正確的熟練度該是多少」 | ⚠️ 不能單從 attempts 推 —— 缺了上線前的歷史 |

所以 `04` 裡兩張表的數字差很多**不一定是 bug**（實測就有一列是舊表 6/6、新表 2/2）。

要算正確值，先看 `mastery_level` 是否等於 `review_count`：
相等就代表每一步都是 `+1`（easy）—— 從 0 起算 n 步最多只能到 n，所以這是唯一解，
正確熟練度 = `review_count − 多算次數`。不相等就得重放，而重放需要上線前的紀錄。

## 已知的邊界

- **`session_id` 是 NULL 的列會被歸在一起**（Postgres 的 PARTITION BY 把 NULL 視為同一組）。
  時間窗仍然在擋，但舊資料若大量沒有 session_id，判讀時要留意。`00` 的第 4 項會告訴你比例。
- **兩個分頁同時作答不會被抓到**（session 不同）。那不是連點，刻意不算。
- 大表上這幾支會做全表的 window function。真的慢的話，在 `scoped` 的 `WHERE` 加一段
  `AND occurred_at >= now() - interval '90 days'`。

## 修正（06 / 07）

`06` 是唯讀預覽，`07` 才會寫。跑 `07` 之前一定要先看 `06` 的每一欄。

`06` 有三道防線，任何一道亮了就代表**那一列不要改**：

| 防線 | 亮的時候代表 |
|---|---|
| `🛑 不一致：分析已過期` | 稽核跑完之後又有新的作答，重跑 01 / 04 |
| `🛑 不可反推`（熟練度 ≠ 複習次數） | 混了 hard / forgot，要重放，而重放缺上線前的歷史 |
| `🛑 不可反推`（複習次數 ≤ 多算次數） | 反推會得 0 或負數 —— 那是算式失效，不是正確值 |

🛑 **`06` 的輸入只有學生 id，單字由資料自己定位。**
`lexical_items.lemma` 沒有 UNIQUE，而且那是刻意的（同形異義允許並存）。
拿 lemma 當鍵可能指到另一個同形的項目 —— 改資料時就是改錯東西。
`06` 會印出 item 的 UUID，`07` 用那個當鍵。

## 驗證這份稽核本身

```bash
bash supabase/tests/lexical-duplicate-audit/run-audit-test.sh
```

從零建一個臨時資料庫，種下已知案例，跑 **00～05 的原檔**（不是複製品），斷言 22 條。

種進去的案例裡有**四組是刻意不該被抓到的對照**：相隔 15 分鐘的真重複、
同一瞬間但不同題型、不同學生、不同 session。
少了它們，這份稽核只證明得了「會抓東西」，證明不了「沒有亂抓」。

修正預覽另有一支：

```bash
bash supabase/tests/lexical-duplicate-audit/run-repair-test.sh
```

跑 `06` 的原檔（只把 target 裡的三個學生 id 換成 fixture 的，邏輯一字不動，
腳本會檢查代換沒有改動行數），斷言 **14 條**。
`lexical_compat_review_interval` 從真正的 migration 抽出來載入，不另寫一份 ——
間隔表哪天改了，這裡要跟著動。

三道防線各有一個 fixture 案例，且突變測試確認拿掉任一道都會紅：

| 拿掉 | 結果 |
|---|---|
| 唯一解判定（熟練度=複習次數） | 對混了 hard/forgot 的列硬算出建議值（3 條紅） |
| 過期偵測 | 過期的分析被標成「一致」（1 條紅） |
| 下限保護（複習次數 > 多算） | 算出 `0` 並當成正確值（1 條紅） |

突變測試也確認過主稽核的斷言真的會紅，包括第一版的那兩個錯：

| 把查詢改回 | 結果 |
|---|---|
| `judgment` 只看 `correct` | SRS 的 forgot+easy 看不見（2 條失敗） |
| 加回「只看四種題型」的過濾 | 組數 7 → 3（6 條失敗） |
| `correct` 加進分組 | 判定矛盾掉到 0 |
| 時間窗放寬到 20 分鐘 | 誤抓相隔 15 分鐘的真重複 |
| 分組不分題型也不分 session | 誤抓不同題型與不同分頁 |
