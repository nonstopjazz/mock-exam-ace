# 題目必填 ＋ 修正差異標示 —— rollout 記錄

> 執行日期：2026-09-24
> 環境：gsat-staging → production，兩邊都完成
> PR：#138（程式與 migration）

這份文件只記錄【事實】：跑了什麼、量到什麼、哪些驗過、哪些沒有。

---

## 1. 為什麼做這兩件事

兩件都是「該有的資訊沒有送到該看的人手上」。

| | 問題 | 後果 |
|---|---|---|
| ② | `essay_topic` 是選填，學生幾乎都留空 | AI 改作文時**不知道題目**，判斷不了有沒有切題；老師端的題目 filter 幾乎沒東西可篩 |
| ③ | 15.2% 的 `correction` 是整句改寫 | 學生看到兩段長得不一樣的英文，**看不出自己哪裡錯** |

執行前在 production 量到：

|---|---|---|
| **39** | 49 | **80%** |

## 3. ② 題目必填

### 做法

擋在**兩支 RPC** 裡，不是只擋前端：

- `submit_writing_essay`（文字作文）
- `create_writing_image_draft`（圖片作文，題目在建草稿時就要）

前端也擋（送出鈕不給按／按了跳提示），但那是體驗，不是規則 ——
直接呼叫 RPC 也繞不過去。

### 🛑 刻意不加 `NOT NULL` 約束

既有 39 列是 null。加 `NOT NULL` 會讓 migration 當場失敗，
而且那些舊作文會變成**不可更新**。回頭去填一個沒有人記得的題目
只是製造假資料。

所以這是「**從現在起必填**」，不是「所有作文都有題目」。

### 本機驗證（用 migration 從零建庫）

| # | 斷言 | 結果 |
|---|---|---|
| — | 改之前兩條路都能留空（先造 2 列 null 當既有資料） | ✅ |
| T1–T3 | 文字作文：NULL／空字串／只有空白 全擋 | ✅ |
| T4–T5 | 圖片作文：NULL／只有空白 全擋 | ✅ |
| T6–T7 | 有填題目仍可送出／建草稿 | ✅ |
| T8 | 題目有 `btrim` | ✅ |
| T9 | 標題檢查仍然先觸發 | ✅ |
| T10 | 既有 null 列原封不動 | ✅ |
| — | 回滾後恢復可留空 | ✅ |
| — | 再執行一次乾淨（`CREATE OR REPLACE` 可重複） | ✅ |

### production 執行結果

| 步驟 | 結果 |
|---|---|
| 執行前 | 題目為空 **39** / 總數 **49** |
| 兩支函式 | `Success. No rows returned` |
| 驗證 | `submit_writing_essay` **true** · `create_writing_image_draft` **true** |
| 執行後 | 題目為空 **39** / 總數 **49** —— **完全一致** |

### 端到端驗證

送出一篇真實作文（production，2026-09-24 06:50:01 UTC）：

```
title        作文測試0924-如果可以選擇你要住在哪裡
essay_topic  如果可以選擇你要住在哪裡        ← 不是 null
```

**送出路徑沒有壞**，而且題目確實落地。這一項比「擋不擋得住空題目」重要 ——
送出路徑壞掉的話學生連作文都交不出來。

### 部署順序

前端的必填改動隨 #138 進 main 並由 Vercel 部署，**早於** production 的 SQL。
方向是「前端比後端嚴格」，不會出事。

反過來（後端先擋、前端還沒更新）會讓學生撞到看不懂的錯誤 —— 沒有走那個順序。

## 4. ③ 修正差異標示

### 原因不是模型不聽話

`api/_lib/writingPrompts.ts` 原本字面寫著：

```
每一筆 finding 都必須給 correction——【改寫後的正確英文句子】。
```

**要求的就是「句子」**，兩個示範也都是整句。15.2% 不是失控，是規格就那樣寫。

### 兩層處理

| | 做法 |
|---|---|
| 治因 | prompt 改成要求「把 quote 修好之後的樣子，**範圍與 quote 相同**」，附擴寫的反例，再加「一筆 finding 只修一個錯誤」 |
| 治果 | 報告與老師端 drill-down 逐詞比對 quote 與 correction，標出差異 |

為什麼兩層都要：prompt 只能降低發生率，不能保證；而且 **quote 本來就是整句時，
correction 本來就會是整句** —— 那時同樣需要標出差異。

### 🛑 刻意不在契約層擋長 correction

`analysisContract.ts` 已經擋掉「correction 與原句相同」。**沒有**再加一條
「不准整句」，因為那會誤殺合法的整句修正，並觸發無謂的重試。

### 實際效果

```
原文  Although the weather was very bad yesterday, [-but] we still decided to [-going] outside …
修正  Although the weather was very bad yesterday, we still decided to [+go] outside …
```

整句改寫現在讀起來就是「動了兩個字」。

### 驗證

`npm run verify:correction-diff` —— **24 條斷言**，涵蓋：

- 誤報（沒改到的字不能被標成改過）
- 漏報（改過的字一定要標出來）
- **重組後與輸入逐字相同**（會吃掉空格的實作在短句上完全正常，
  要等長句才會讓學生看到黏在一起的英文）
- 只加字 / 只刪字 / 大小寫
- 退化情況：空字串、只有空白、超過 token 上限、完全無關
  （最後一種直接純文字呈現 —— 整段紅綠等於沒標）

⚠️ **模型端沒有驗到。** prompt 改了之後還沒有統計新的整句改寫比例。
要有結論得累積一批新分析再重跑一次比例查詢。目前只能說「原因找到了、改了」，
不能說「15.2% 降到多少」。

## 5. ⚠️ 環境限制：整份檔案執行失敗，分段成功

2026-09-24 在 Supabase SQL Editor 執行原本的單一檔案
（`require_essay_topic.sql`，內含兩支函式）時：

```
ERROR: 42601: syntax error at or near "RAISE"
LINE 1:     RAISE EXCEPTION '請先登入' USING ERRCODE = '28000';
            ^
```

本機把**那一行單獨**餵給 psql，錯誤訊息與位置完全重現。
所以伺服器收到的是函式本體裡的**片段**，不是整份檔案。

同樣的內容**分成兩段各自貼上，兩段都成功**（staging 與 production 皆是）。

### 🛑 原因沒有查明

一開始的解釋是「工具切語句時沒認得 `$$`」。**那個解釋站不住腳**：
`create_lexical_core.sql` 的 trigger 函式本體裡有 **5 個分號**，
整份貼上卻執行成功。

所以這裡不宣稱知道為什麼，只記錄已經驗證過的事實與繞過方式。

### 採取的做法

把那支 migration 拆成【一個檔案一支函式】：

```
require_essay_topic_1_text.sql        + .rollback.sql
require_essay_topic_2_image.sql       + .rollback.sql
require_essay_topic_verify.sql        （唯讀驗證）
```

拆開後的函式定義與 production 實際執行的內容**逐字相同**（用 diff 驗過），
10 項斷言重跑全過。

⚠️ **這不是通則。** 多數多函式的 migration 整份跑都沒問題。
這是這一支的已知地雷，不需要回頭去拆其他檔案。
